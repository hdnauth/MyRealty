## 2. 입지 점수: 지역 단위 미리 계산 + 화면 단위 즉석 보충 ✅

순수 즉석 계산만으로는 부족하다 — 계산은 빠르게 만들 수 있어도 **시설 자료가 없는 곳은 점수가 낮게 틀어진다**. 그래서 두 층으로 나눴다.

### 2.1 미리 계산(주력) — ETL

- **단지 격자 수집**(`jobs/pois_job.collect_cells`): 수집 지역 아파트 단지가 있는 0.01° 칸(약 0.9×1.1km)마다 칸 중심에서
  상가정보 1.8km · 병원 6km · OSM 2.5km(밀집 시설 1.8km). 칸 중심에서 가장 먼 단지가 약 0.71km 라 칸 안 모든 단지의
  "1km 안 학원·의원·음식점"을 빠짐없이 센다. 다 받으면 `poi_cells` 에 적는다(키가 있으면 상가정보까지 받아야 완료).
  - 운영 DB 기준 132칸. 하루 30칸(공공 API 칸당 약 6회) · 시간 예산(`DAILY_BUDGET_MIN`) 안에서 — 약 5일이면 전부, 이후 30일마다 갱신.
  - 아직 안 받은 칸 → 단지 많은 칸 순.
- **시설이 갖춰진 단지 전부 계산**(`analytics/location.compute_locations`): `poi_cells` 칸 안 또는 관심 부동산 500m 안 단지.
  매일은 점수가 없거나·간이거나·30일 지났거나·칸을 다시 받은 뒤 계산 안 한 아파트만 다시 계산한다.
  시설이 갖춰지지 않은 곳의 예전 점수(`basis = 'full'`)만 지우고, 웹의 간이 점수는 남긴다.
- **시설 조회 최적화**(`POI_SQL`): 밀집 시설(음식·카페·편의점·학원·의원·버스)은 1km, 나머지는 5km 상자(`ST_Expand`)로 먼저 걸러
  공간 인덱스를 탄다. 점수 공식이 밀집 시설을 1km 넘게 쓰지 않음을 테스트로 고정했다. 측정: 시설 2,253건 지점 **16ms**(이전 41~326ms), 결과 동일.

### 2.2 즉석 보충(빈틈) — 웹

새로 켠 지역·새 단지·오피스텔/빌라·오래된 점수를 채운다. `GET /api/map/location?ids=…` → `lib/queries/location-live.ts`.

| 지도 확대 | 동작 |
|---|---|
| 14 이하 | 이미 계산된 점수만(집계 API 의 `loc_score`) |
| **15 이상**(휴대폰 폭 약 1.5km) | 지도가 멈추고 0.6초 뒤 화면 안 점수 없는 단지 **최대 30곳**을 가운데에 가까운 순으로. 지도를 다시 움직이면 요청을 끊고(서버도 남은 계산 중단), 한도 때문에 남은 단지(`pending`)는 1.5초 뒤 다시(한 화면 최대 4번) |
| 단지를 누름 | 확대와 상관없이 그 단지 하나를 우선(`priority=1`) — 항목별 막대까지 |
| 단지 상세 화면 | 서버에서 바로 계산(full), 시설이 없으면 화면에서 간이 계산 요청 후 다시 그림 |

- **full**: 시설이 갖춰진 단지 — ETL 과 같은 쿼리·공식으로 계산해 `location_scores` 에 저장(요청당 10곳).
- **quick(간이)**: 그 밖 — OSM 에서 역·학교·공원·병원·마트만 보충(단지 ±2km)해 그 항목 + 직주근접으로 계산, `basis = 'quick'`.
  학원·음식·의원·버스는 '미수집'으로 빠지고 나머지 비중으로 다시 나눈다. 요청당 3곳, OSM 은 최대 10초, 실패하면 그 인스턴스는 1분 쉰다.
  화면에 "간이" 표시, **백분위 비교에서는 빠진다**. 다음 매일 수집이 그 칸을 모으면 full 로 바뀐다.
- 부하 상한: 요청당 단지 40곳·계산 시간 20초, IP 별 분당 30회(인스턴스 메모리), 저장된 점수는 다시 계산하지 않음(45일), 응답은 남은 단지가 없을 때만 60초 캐시.

### 2.3 Python ↔ TypeScript 일치

점수 공식은 웹에 TypeScript 로 옮겼다(`lib/location-score.ts`). 두 구현이 어긋나지 않도록:
- 같은 입력·기대값 묶음 `apps/web/src/lib/__tests__/fixtures/location-parity.json` 을 Python(`tests/test_location_parity.py`)이 만들고,
  양쪽 테스트가 확인한다. 공식을 바꾸면 `UPDATE_LOCATION_PARITY=1 uv run pytest tests/test_location_parity.py` 후 웹을 맞춘다.
- 동점일 때 행 순서에 따라 결과가 달라지지 않게 가까운 순으로 정렬해 고른다(양쪽 동일).
- 운영 데이터 13곳(관심 부동산 7 + 단지 6)에서 총점·항목 점수·시설 이름이 모두 같았다.

### 2.4 데이터 모델

- `poi_cells(cx, cy, sources, fetched_at)` — 다 받은 격자(마이그레이션 0019).
- `location_scores.basis` — `full` | `quick`.

## 3. 글자 · 아이콘 · 터치 크기 ✅

- **글자 체계**(`globals.css @theme`): `text-xs` 12→13px, `text-sm` 14→15px. px 로 박힌 크기는 rem 으로 바꾸고 **최소 12px**(10·11px 없앰).
- **설정 › 글자 크기**: 보통(15px) · **크게(기본, 16px)** · 더 크게(18px). 화면 테마와 같은 쿠키 + 첫 페인트 전 스크립트(`lib/font-size.ts`).
- 버튼 높이 40→44px, 칩 약 26→34px, 차트 기간 버튼은 보이는 크기보다 누르는 영역을 넓힘(`.hit`).
- 하단 탭 아이콘 22→24px(높이 56px), 사이드바 줄 36→44px·아이콘 17→20px, 카드 제목 14→16px, 숫자(Stat) 18→20px.
- 지도: 가격 라벨 11→13px(겹침 정리 상자도 키움), 시설 아이콘 22→26px, 개발·입주·청약 라벨 11→12px, 목록·선택 카드 글자 한 단계씩.

## 4. 차트 ✅

- **기간 선택 공통화**(`components/charts/range-chips.tsx`, `lib/chart-range.ts`): 1년·3년·5년·10년·전체 — 자료가 실제로 걸친 기간보다 짧은 것만 보인다. 기본 3년.
  실거래 차트·모든 지표 차트(`LineSeriesChart`)·시장 요약 차트에 적용.
- **x축**: 1월은 굵은 "2025년", 그 밖은 "24년 4월"(눈금이 1월에 오지 않아도 해가 늘 보임). **툴팁** 머리는 "2025년 3월"(실거래 점은 "2025년 3월 15일").
- 지도 단지 카드의 점 그래프: 해가 바뀌는 곳 세로 눈금·"2025년", 양 끝 "25년 3월", 매매/전세 범례, 글자 9→11px.
- 모바일 핀치 확대(dataZoom)는 넣지 않았다 — 세로 스크롤을 가로채서. 기간 버튼으로 대신한다.

## 5. 관심 화면 ✅

순서: **관심 부동산(최대 6개, 더 보기) → 보유 자산 숫자(한 달 변화) → 오늘 요약 → 이번 주 새 거래 → 최근 소식·동네·일정**.
카드 아래에 같은 단지·평형 **최근 12개월 월 중위가 추세선**과 1년 변화(최근 3개월 ÷ 12~15개월 전, 양쪽 2건 이상)를 카드 폭 전체로(`itemTrends`).

## 6. 시장 화면: 그래픽 먼저 ✅

요약 탭 맨 위에 **가격지수(선) + 월 매매 건수(막대)** — 단위가 달라 한 축에 겹치지 않고 x축을 함께 쓰는 위아래 두 칸, 십자선·툴팁이 함께 걸림,
집계 중인 이번 달 막대는 흐리게(`components/indicators/market-hero.tsx`). PC 는 옆에, 모바일은 아래에 **짧은 판정 카드**(이유는 제목만, 설명은 펼쳐서).
그 아래 숫자 타일 4개(84㎡ 중간 가격·전세가율·월 매매·시장 온도)에 최근 2년 추세선.
